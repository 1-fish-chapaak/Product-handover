# AI Insight Qualification Criteria
### When does something become an insight, and when is it just an exception?

**Audience:** dev and AI teams building the Insight engine · **Owner:** Product · **Date:** July 2026 · **Version:** 1.0
**Companion docs:** AI-INSIGHTS-METRICS.md, AI-INSIGHTS-RECOMMENDATIONS-MAP.md

---

## 1. The one rule

> **An insight is something a single row cannot tell you. If one row can tell you, it is an exception, and it already has a home.**

The engine notices far more than a person should read. If we surface everything, the finding that matters drowns and people stop opening the panel. This document defines the bar a candidate must clear, the things the model may never say, and the tests QA can run.

Two halves, and they must stay separate:

- **The gate** decides whether a candidate qualifies at all. It is deterministic and runs **before** the model is called. No model judgment.
- **The narration rules** constrain what the model may say once a candidate has qualified. The model describes the evidence bundle. It never computes, never infers a share, never asserts a cause as fact.

---

## 2. Why this exists: a real card that should never have shipped

This card was generated by the current engine. It is our reference failure. Everything in this document exists to reject it.

> **"Merchant 8116129230 represents one-third of the current Amex reconciliation exceptions"**
> Medium · 78% confidence
> "Merchant 8116129230 accounts for 1 of the 3 Amex reconciliation exceptions flagged this run, about **33% of the current exception population**."
> "Across the examined window, merchant 8116129230 has **1 flagged row** and appeared in **1 of 1 runs** reviewed."
> "Because merchant 8116129230 appeared in 1 of 1 runs reviewed, the current known unresolved pattern is **100% of the available run history**."
> Then 5 recommended actions: pull the statement, check the mapping, confirm with Amex, track to closure.

It is **one row wearing the costume of a pattern.** Four specific defects:

| # | Defect | Why it is wrong |
| --- | --- | --- |
| 1 | "1 of 3, about 33% of the population" | With 3 exceptions, **every** exception is 33%. If the 3 rows sit under 3 merchants, all three are "33% concentrations." The percentage carries zero information. Small denominators make anything look big. |
| 2 | "1 of 1 runs, 100% of the available run history" | One run is not history. 1 of 1 is always 100%. This is a tautology printed as evidence. |
| 3 | The 5 actions are "go investigate this exception" | Pull the statement, check the mapping, confirm, track to closure. That is what an analyst does with **every** flagged row. The card adds no decision the workflow did not already imply. |
| 4 | "78% confidence" on 1 row, 1 run | Asserted, not earned. Nothing in the evidence supports it. |

**Root problem:** the bar had no minimum size. A one-row exception was allowed in as an "early signal," and the model was free to compute percentages on a base of 3.

## 3. There are only two doors in

A candidate must enter through one of these. Nothing else qualifies.

| Door | What it means | Minimum to enter |
| --- | --- | --- |
| **A. It is a pattern** | Several things point the same way, and no single row reveals it | **At least 2 supporting items** (2+ rows, 2+ runs, or 2+ workflows) **and** the pattern must be real per the size rules in section 5 |
| **B. It is one item big enough to matter alone** | A single row, but the money or the risk carries it | Clears the **materiality floor**, **or** it is a fraud / governance item / contradicts an approved control |

**The Amex card enters neither.** One row (fails A). $4,200 with no fraud or governance angle (fails B). It is an exception. Route it to the exception queue, where the analyst would have found it anyway.

## 4. The gate: five tests, in order

Run cheapest first. Failing any test stops evaluation. **The model is only called after a candidate passes all five.**

| # | Test | Rule (deterministic) | On failure |
| --- | --- | --- | --- |
| 1 | **Is it more than one thing?** | `supporting_items >= 2` OR (single item AND (`materiality >= floor` OR `is_risk_item`)) | **Reject.** Route to the exception queue. |
| 2 | **Is it a finding, not a number?** | A baseline exists: `expected` and `observed` are both populated, and `observed` breaches `expected` | **Reject.** It is a stat. |
| 3 | **Is it true enough to act on?** | Recurrence/trend claims require `runs_analysed >= 2`. If `runs_analysed <= 2`, cap confidence and set `evidence_label = "early signal"` | **Do not reject.** Cap and label. Never reject a thin but material finding. |
| 4 | **Does it matter?** | `materiality >= engagement_floor` OR `is_risk_item` (fraud, governance, contradicts an approved control, related party, regulatory) | **Reject** to a logged, retrievable drawer. Never silently drop. |
| 5 | **Is it news, and does it change what I would do?** | Not a stale repeat (`novelty >= floor`, or it escalated), AND `recommended_action != default_exception_handling` | **Demote** to a quiet digest line. Do not render a card. |

Passing all five means the candidate **qualifies**. Qualifying is not the same as showing. Qualifiers are then ranked and only the top ones fill each surface's fixed slots (see AI-INSIGHTS-METRICS.md, the attention budget).

### Decision flow

```
candidate
  ├─ Gate 1  support        → fail → REJECT, route to exception queue
  ├─ Gate 2  baseline       → fail → REJECT, it is a stat
  ├─ Gate 3  evidence       → thin → CAP confidence + label "early signal" (never reject)
  ├─ Gate 4  materiality    → fail → REJECT to logged drawer
  ├─ Gate 5  novelty+action → fail → DEMOTE to digest
  └─ QUALIFIES → call the model to narrate → rank → fill surface slots
```

## 5. The "never print this" rules (for the AI team)

These are **output constraints on the narration layer**. Every one of them was broken by the Amex card. The model receives a pre-computed evidence bundle and may only describe what is in it. It must never compute a share, a ratio, or a history claim itself.

| Rule | Threshold | What it kills |
| --- | --- | --- |
| **No percentage unless the population is at least 20.** Below that, state counts. | `population >= 20` to emit any share | "About 33% of the current exception population." Must read "1 of 3." |
| **No recurrence or history claim on fewer than 2 runs.** | `runs_analysed >= 2` | "100% of the available run history." "Appeared in 1 of 1 runs" may be stated as a fact but never as a pattern. |
| **No "concentration" unless the top name is at least 40% of the population AND at least 3x the runner-up.** | `top_share >= 0.40 AND top_count >= 3 * runner_up_count` | 1-1-1 is uniform, not concentrated. MCKESSON passes: 78%, and 70 vs 10 is 7x. |
| **Confidence is capped when evidence is thin.** | `runs_analysed <= 2` → confidence cannot present as proven; label "early signal, not a trend" | The "78% confidence" pill on one row. |
| **The model never asserts cause as fact.** | Cause is always phrased as a candidate to confirm | "The feed **is** broken." Must read "Likely cause, confirm before relying on it." |

**Implementation note for the AI team:** the gate computes `population`, `top_share`, `runner_up_count`, `runs_analysed`, `supporting_items`, and `materiality`, and passes an `allowed_claims` set into the prompt. If `population < 20`, no share phrasing is permitted in the bundle at all. The cleanest guard is to **not put the percentage in the bundle**, so the model has nothing to print.

## 6. Metrics

| Metric | How we measure it | Target |
| --- | --- | --- |
| **Minimum support** | Insights standing on 2+ items, or a single item clearing materiality / risk / all insights surfaced | 100% |
| **Share-claim validity** | Share claims made on a population of 20+ / all share claims | 100% |
| **Recurrence-claim validity** | History or recurrence claims backed by 2+ runs / all such claims | 100% |
| **Concentration validity** | Concentration claims where top >= 40% and >= 3x runner-up / all concentration claims | 100% |
| **Thin-evidence honesty** | One-run insights labelled "early signal, not a trend" / all one-run insights | 100% |
| **Action distinctiveness** | Insights whose action differs from default exception handling / all insights | 100% |
| **Hallucinated-figure rate** | Numbers in the narration absent from the evidence bundle / all numbers in narration | 0% |
| **Insight precision** | Insights the user acted on / insights shown | 70%+ |

## 7. Acceptance test cases

QA should be able to run these two as the canonical pass/fail pair.

| | **Amex merchant 8116129230** | **MCKESSON** |
| --- | --- | --- |
| Supporting items | 1 row → **fails Gate 1** | 70 rows → passes |
| Population | 3 (too small for any %) | 90 → share claims allowed |
| Concentration | 1 of 3, uniform → no concentration claim allowed | 78%, 7x the runner-up → allowed |
| Runs | 1 → no history claim allowed | 1 → allowed, labelled "early signal" |
| Money | $4,200, below floor, no risk angle → **fails Gate 4** | Real underpayment → passes |
| Action | "Investigate the row" = the day job → **fails Gate 5** | "Hold 70 lines before settlement" → passes |
| **Expected result** | **REJECTED.** Never renders as an insight. Routes to the exception queue. | **QUALIFIES.** Renders as a one-run concentration, labelled early signal. |

**Regression rule:** if a change to the engine would let the Amex card render as an insight, the build fails.

Additional cases worth covering:

1. A run with 3 exceptions across 3 merchants produces **zero** insights, not three "33% concentrations."
2. A single $4m unmatched item with no recurrence **does** qualify, via Door B (materiality).
3. A run contradicting an approved control qualifies **even at $0**, via Door B (risk item).
4. The same low-value warning dismissed 3 times stops rendering as a card and becomes a digest line.

## 8. Fixed vs tunable

| Setting | Value | Status |
| --- | --- | --- |
| Minimum supporting items | 2 | **Fixed.** This is what stops a row cosplaying as a pattern. |
| Recurrence requires runs | 2 | **Fixed.** One run is never history. |
| Population floor for a share claim | 20 | Tunable |
| Concentration bar | top >= 40% and >= 3x runner-up | Tunable |
| Materiality floor | engagement-set | Tunable, set per engagement |
| Novelty floor | starting conservative | Tunable per pattern once we see accept/dismiss rates |

---

## 9. Open items

1. **Per-pattern materiality floors.** A governance conflict should surface at a lower bar than a low-value efficiency gap. We start with one conservative floor and split it once we have real accept-and-dismiss data.
2. **Default-action comparison (Gate 5).** We need a machine-checkable definition of "the workflow's default exception handling" to diff a recommended action against. Proposal: a per-workflow `default_disposition` string that the gate compares against.
3. **Materiality floor source.** Whether this is inherited from the engagement's materiality or set per workflow.
