00 — Orientation

How to read this

The PRD says what to remember, surface by surface. It deliberately stops short of the components themselves — the closing “design scope” section was never written, and Knowledge Hub has no metrics block. This plan fills both gaps and makes three arguments:

  • Memory is one product, not six features. The same five or six UI moments repeat in every surface’s use cases. Design them once as a kit (§03), and every surface becomes an arrangement of known parts.
  • Trust is the design constraint. This is an audit product: a silently-applied memory that’s wrong produces a confident wrong number. Every treatment below follows one constitution (§02) — visible, attributed, human-gated, undoable, logged.
  • The plumbing is the first deliverable. Today the registry has no readers, the governance surfaces named in our own copy don’t exist, and two disconnected stores hold the same facts (§01). Phase 0 fixes the spine before any surface gets its moments.

Each §04 table covers every use case in the PRD for that surface — nothing is dropped; a few are pushed back on, marked PB-n and argued in §08. Phase pills: P0 spine P1 flagship P2 behavioral P3 polish. Rev 2: §09 is the authoritative build list — it re-sorts everything here into four tiers, including the use cases that need no new UI at all.

02 — The spine

One store, one grammar

Taxonomy: adopt the PRD’s 7 kinds × 5 scopes

Every “Stored as” label in the PRD resolves to this matrix. Our current store is close but not aligned — the migration is small and worth doing before anything visible is built D1:

Kind ↓ · Scope →PersonalTeamEngagementOrganizationwas “tenant”Sourcenew

Routinenew a job that repeats on a rhythm●●———
Vocabulary what words mean here●●●—●

Retired: convention (its rows become Preference·Team). The badge grammar everywhere is Kind · Scope — e.g. Decision · Source — the same two words the PRD uses, so the doc and the product speak one language.

Lifecycle: five states, not two

proposed → active → (retired | expired | superseded). “Proposed” replaces today’s pending and is the state My Queue works. Personal memories skip the queue — they activate instantly with a visible undo (that’s what the PRD’s “undo rate on just-learned rows” metric measures). Source memories carry the schema fingerprint they were written against; a fingerprint mismatch moves them to a drifted flag that §04f’s drift review works through. Nothing is ever hard-deleted: retired rows keep their audit trail and can re-surface if the signal strengthens (consistent with edge case M4 in the engine PRD).

The rule of 2–3: when learning fires

The PRD is remarkably consistent about thresholds. Codify it once so every surface behaves identically:

1 occurrenceNever learn from a single event — except an explicit answer the user gives (a clarification, a correction, “match my March report”). Explicit teaching is always instant.capture, not inference
2nd occurrenceRecognize and offer: run shape recognized → replay offer; mapping confirmed twice → memory updates; word corrected twice → offer the vocabulary rule.offer, don’t assume
3 consistent signalsBehavioral defaults flip: chart type, %-vs-counts, export format, drill path, recurring report, rhythm. Three dismissals demote a widget.default, with a visible badge

The constitution

Eight rules, carried forward from the engine PRD’s UI rules and extended. Every §03 component and §04 treatment obeys them; anything that can’t is redesigned until it does.

  1. Always attributed. Every recalled value names its source and age. No unsourced “AI knows.”
  2. Applied is visible. A memory that acted leaves a mark — a chip, a badge, a report line. “Applied silently” exists nowhere; even the PRD’s “silent” carve-outs are shown as removable chips.
  3. Personal learns instantly, shared learns through a human. Personal = act + undo. Team/Engagement/Organization/Source = proposed → My Queue. The gate is never skippable and never auto-approves.
  4. Warnings, not errors. Drift and conflicts are findings. They block trust, not the run — amber, with the evidence, never a red stack trace.
  5. Rules have no override control. Sensitivity masking and org content rules are enforced and reported. The UI shows that the rule fired; it offers no way around it.
  6. Offer before assuming; 2–3 signals before defaulting. Per the threshold table. Declining an offer is itself a signal — decay it, don’t re-ask weekly.
  7. Demote, decay, never delete. Undo on everything just-learned; retired ≠ erased; a dismissed insight may return if the signal strengthens.
  8. Every change is logged. Learn, apply-with-effect, approve, retire, renew, drift-update — all land in the audit log’s new Memory module with actor and evidence.

06 — Measurement

Metrics, and what the prototype can honestly show

The PRD’s per-surface metrics stand as written (re-ask → 0, setup −70%, golden-record >80%, edit distance falling, default acceptance, undo <10%). Two additions:

  • Knowledge Hub metrics (filling the PRD gap): definition coverage (% of active-source columns with meaning/role), clarification deflection (source questions answered from memory), drift caught before run (target 100% — the executor banner is the backstop, not the catch), and definitions captured per week (is the moment-of-confusion pipe actually writing?).
  • One health view, not six: a “Memory health” band on Smart Learn — recalls this week, questions spared, undo rate, coverage — replacing today’s decorative counts with the real write-path numbers. Per-surface metrics stay in the PRD/analytics, not in product chrome.

Prototype honesty: the demo seeds recall counts and coverage, but every counter shown is wired to the session’s real events (a capture increments, an undo decrements) so the demo behaves truthfully even where history is seeded — same determinism rule as the rest of the repo, no Date.now().

What follows is the definitive list: the registry design first, then every change in four tiers. 9 kit components · 6 new surfaces/sections · 28 wiring points · 12 no-UI upgrades.

Smart Learn: one registry, three axes, zero new chrome

The complexity risk is real: 60-odd memories across 5 scopes × 7 kinds, firing on 6 surfaces, is three filter dimensions plus search — a faceted-search UI nobody asked for. The design principle that keeps it calm: each axis gets exactly one job.

  • Scope structures the page. The existing scope sections (closest-to-you first) stay the only top-level organization, with Source joining as a fifth section. Scope is how people ask the question — “what does IRA know about me / my team / this engagement / the org / this data.”
  • Kind badges the row. The kind icon + label lives on the row (as today), never as page structure. Nobody browses “all Corrections”; they recognize a row by its statement and confirm by its badge.
  • Surface filters. “Fires in” (Chat · Runs · Engagements · Reports · Dashboards) becomes real row metadata — the existing readBy field, finally wired — shown as quiet mono chips on the meta line. Want only report memories? One pick in the filter menu.
  • One filter menu instead of three. The existing status dropdown grows into a single Filter menu with three sections — Status · Kind · Fires in — each single-select with live counts. Net new controls on the toolbar: zero. Search already spans statement, source, and kind; it gains surface labels.
  • Entity sub-groups where scope has entities. Engagement and Source sections group rows under their entity (“Pharma Chargeback FY26 · 8”, “vendor_master_v2 · 6 · 1 drifted”), collapsed by default with counts and attention badges. Personal, Team and Organization stay flat lists — they’re singular.
  • Deep links both ways. Every row keeps the drawer and safe inline actions (forget / renew / undo) and gains “Open where it fires →”; every home surface (engagement tab, source panel, avatar drawer) gets a “View in Smart Learn” backlink. Registry answers what and why; homes stay where the work happens.
